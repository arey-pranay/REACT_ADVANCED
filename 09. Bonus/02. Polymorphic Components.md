# React — Polymorphic Components

## 1. What is a polymorphic component?

A polymorphic component is a component that can render as different underlying elements or components while keeping a consistent API.

For example, imagine a reusable `Text` component. Sometimes you want it to render as a paragraph, sometimes as a heading, and sometimes as a `span`.

Instead of creating three separate components, you can let the caller choose the rendered element.

AS A HEADING

# Hello, world!

Rendered using an `h1` element.

AS A PARAGRAPH

&#x20;Hello, world!

Rendered using a `p` element.

AS A SPAN

Hello, world!

Rendered using a `span` element.

The important distinction is that the component's implementation is reusable, but the rendered element is configurable.

## 2. The problem polymorphic components solve

Without polymorphism, you might create separate components:

```
function Heading({ children }: Props) {
  return <h1>{children}</h1>;
}

function Paragraph({ children }: Props) {
  return <p>{children}</p>;
}

function InlineText({ children }: Props) {
  return <span>{children}</span>;
}
```

This can duplicate styling and other shared logic.

A polymorphic component lets you choose the element through a prop, often called `as`:

```
<Text as="h1">Hello, world!</Text>
<Text as="p">Hello, world!</Text>
<Text as="span">Hello, world!</Text>
```

Here, `Text` can own the shared styling while the caller chooses the semantic HTML element.

## 3. Basic implementation

In React, HTML elements can be selected dynamically using a variable whose value is the element type.

```
import type { ReactNode } from "react";

type TextProps = {
  as?: "h1" | "p" | "span";
  children: ReactNode;
};

function Text({ as: Component = "p", children }: TextProps) {
  return <Component className="text">{children}</Component>;
}
```

Usage:

```
<Text as="h1">Page title</Text>
<Text as="p">Description of the page.</Text>
<Text as="span">Inline text</Text>
```

### Understand this syntax

```
function Text({ as: Component = "p", children }: TextProps)
```

- `as` is the prop supplied by the caller.
- `Component` is the local variable receiving that prop.
- `= "p"` supplies a default when `as` is omitted.
- `<Component>` renders whichever element type is stored in that variable.

The alias matters because JSX treats lowercase tag names as intrinsic elements, such as `<div>`, while uppercase names such as `<Component>` are treated as variables referring to components or element types.

This implementation is polymorphic, but its TypeScript API is still limited: it doesn't yet accept all the correct attributes for each selected element.

## 4. The real challenge: TypeScript prop safety

Consider:

```
<Text as="a" href="/about">
  About
</Text>
```

A good polymorphic API should allow `href` when rendering an anchor.

But it should reject:

```
<Text as="p" href="/about">
  About
</Text>
```

`href` is not a valid attribute for a paragraph element.

The component should also accept element-specific props such as `target` for an anchor or `type` for a button.

This is where polymorphic component typing becomes more interesting: the allowed props must depend on the selected element type.

## 5. A more reusable TypeScript implementation

A common approach is to use a generic type parameter for the element type and combine its native props with the component's own props.

```
import type {
  ComponentPropsWithoutRef,
  ElementType,
  ReactNode,
} from "react";

type TextOwnProps = {
  children: ReactNode;
  color?: string;
};

type PolymorphicProps<C extends ElementType> =
  TextOwnProps & {
    as?: C;
  } & Omit<ComponentPropsWithoutRef<C>, keyof TextOwnProps | "as">;

function Text<C extends ElementType = "p">({
  as,
  children,
  color,
  ...rest
}: PolymorphicProps<C>) {
  const Component = as ?? "p";

  return (
    <Component style={{ color }} {...rest}>
      {children}
    </Component>
  );
}
```

Example usage:

```
<Text>Default paragraph</Text>

<Text as="h1" id="page-title">
  Page title
</Text>

<Text as="a" href="/about" target="_blank">
  About
</Text>

<Text as="button" type="button" onClick={() => alert("Clicked")}>
  Click me
</Text>
```

The generic parameter `C` represents the chosen element type. `ComponentPropsWithoutRef<C>` obtains the props appropriate to that element, while `Omit` prevents conflicting definitions of props owned by `Text`.

TypeScript caveat: this is a useful general pattern, but production-quality polymorphic typings can need additional handling for generic inference, refs, and conflicts between custom and native props. Compile and test the API against the React and TypeScript versions used by your project.

## 6. Polymorphic components are not limited to HTML elements

The `as` prop can also accept a custom React component, provided its props are compatible with the polymorphic API.

```
function LinkButton({ children }: { children: React.ReactNode }) {
  return <a className="button-link">{children}</a>;
}

<Text as={LinkButton}>Open page</Text>
```

This works with the broad `ElementType` approach above because `LinkButton` is a valid component type and accepts `children`.

However, not every custom component accepts the same props. If you pass additional props, the type system should verify that the chosen component supports them.

## 8. Common mistakes

- Changing the tag without considering semantics. Rendering a clickable action as a paragraph doesn't make it an accessible button.
- Accepting arbitrary props without proper typing. The API should reflect the selected element's supported attributes.
- Using polymorphism everywhere. If a component only needs to render one element, a generic `as` prop adds unnecessary complexity.
- Assuming polymorphism means multiple visual styles. It primarily concerns the rendered element or component; styling variants are a separate concern.
- Ignoring refs. If consumers need access to the underlying DOM node, ref forwarding and its typing must be designed deliberately.

## 9. Compare related React concepts

| Pattern               | What varies or gets reused?                       |
| --------------------- | ------------------------------------------------- |
| Wrapper component     | Surrounding layout or behavior                    |
| Props composition     | Content and behavior supplied through props       |
| Render props          | A function supplied to determine rendered content |
| Custom hook           | Reusable stateful logic                           |
| Polymorphic component | The underlying rendered element or component      |

These patterns can be combined. For example, a polymorphic `Box` can also act as a wrapper, accept `children`, and use custom hooks internally.

## Interview revision

A polymorphic component renders different underlying elements or components based on a prop, commonly `as`. It allows a design system to reuse styles and behavior while preserving semantic flexibility. In TypeScript, a generic element type combined with `ComponentPropsWithoutRef<C>` and `Omit` can make the allowed props depend on the selected element.

Mental model: One component API, multiple possible rendered element types, with the right props for the chosen type.
