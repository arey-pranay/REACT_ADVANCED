# React Patterns: Render Props vs Custom Hooks

The two implementations solve the same problem: tracking the mouse position and displaying its X and Y coordinates. However, they demonstrate two different ways of sharing reusable behavior between React components.

We'll examine the code, understand the data flow, derive why each pattern works, compare their trade-offs, and identify when to use each one.

# 1. Implementation A — Render Props

## The code

```
import "./App.css";
import { DisplayMousePos } from "./components/render-props/display-mouse";
import { RenderMousePosition } from "./components/render-props/render-mouse";

function App() {
  return (
    <div className="container">
      <RenderMousePosition>
        {({ x, y }) => (
          <DisplayMousePos x={x} y={y} />
        )}
      </RenderMousePosition>
    </div>
  );
}

export default App;
```

There are three important participants:

| Participant           | Responsibility                                             |
| --------------------- | ---------------------------------------------------------- |
| `App`                 | Composes the components together.                          |
| `RenderMousePosition` | Owns the mouse-tracking behavior and supplies coordinates. |
| `DisplayMousePos`     | Displays the supplied coordinates.                         |

We can understand the design by looking at the responsibilities separately.

## 1.1 What is a render prop?

A render prop is a prop that is a function used to determine what a component renders.

In this example:

```
<RenderMousePosition>
  {({ x, y }) => (
    <DisplayMousePos x={x} y={y} />
  )}
</RenderMousePosition>
```

The function is passed as the `children` prop. React supports functions as children when a component explicitly invokes them.

Conceptually, `RenderMousePosition` might be implemented like this:

```
import { useState } from "react";

type Position = {
  x: number;
  y: number;
};

type Props = {
  children: (position: Position) => React.ReactNode;
};

export function RenderMousePosition({ children }: Props) {
  const [position, setPosition] = useState<Position>({
    x: 0,
    y: 0,
  });

  function handleMouseMove(
    event: React.MouseEvent<HTMLDivElement>
  ) {
    setPosition({
      x: event.clientX,
      y: event.clientY,
    });
  }

  return (
    <div onMouseMove={handleMouseMove}>
      {children(position)}
    </div>
  );
}
```

This is an illustrative implementation of the pattern, not necessarily the exact code in your project.

Notice the critical line:

```
{children(position)}
```

The component invokes the function and passes it the current position.

The function receives the position and returns React elements:

```
({ x, y }) => (
  <DisplayMousePos x={x} y={y} />
)
```

The returned element becomes part of the rendered tree.

The key idea: the component that owns the behavior doesn't need to know which UI the consumer wants to render. It supplies data; the consumer supplies a function describing the UI.

## 1.2 How does the data flow?

Mouse movement

A mouse event occurs

`RenderMousePosition`

Updates its position state

`children(position)`

Calls the consumer's rendering function

`DisplayMousePos`

Receives x and y as props

When the mouse moves:

1. The event handler updates the position state.
2. React schedules and performs the relevant render.
3. `RenderMousePosition` calls its `children` function with the updated position.
4. That function returns a `DisplayMousePos` element with the new props.
5. React updates the displayed output as needed.

This lets the mouse-tracking component reuse the same behavior with different render functions.

## 1.3 Why is this useful?

Imagine you want to reuse mouse tracking for three different purposes:

```
<RenderMousePosition>
  {({ x, y }) => <DisplayMousePos x={x} y={y} />}
</RenderMousePosition>
```

```
<RenderMousePosition>
  {({ x, y }) => (
    <p>Mouse is at ({x}, {y})</p>
  )}
</RenderMousePosition>
```

```
<RenderMousePosition>
  {({ x, y }) => (
    <div style={{ left: x, top: y }}>
      Custom cursor
    </div>
  )}
</RenderMousePosition>
```

All three consumers can reuse the same tracking component while rendering different UI.

That is the original motivation for the pattern: separate reusable behavior from the decision about what to render.

# 2. Implementation B — Custom Hook

## The code

```
import "./App.css";
import { useMousePosition } from "./components/hook/useMousePosition";

function App() {
  const { x, y, onMouseMove } = useMousePosition();

  return (
    <div className="container">
      <div
        className="relative-container"
        onMouseMove={onMouseMove}
      >
        <section className="absolute-section">
          <p>
            <span className="bold-span">X</span>: {x}
          </p>
          <p>
            <span className="bold-span">Y</span>: {y}
          </p>
        </section>
      </div>
    </div>
  );
}

export default App;
```

Here, there are two important participants:

| Participant        | Responsibility                                                        |
| ------------------ | --------------------------------------------------------------------- |
| `useMousePosition` | Encapsulates reusable mouse-tracking logic and returns its interface. |
| `App`              | Calls the hook, attaches the handler, and decides what UI to render.  |

Unlike the render-props implementation, the hook does not need to return a React element or accept a render function.

## 2.1 What does a custom hook do?

A custom hook is an ordinary JavaScript function that uses React Hooks to encapsulate reusable logic.

An illustrative implementation might look like this:

```
import { useState } from "react";

export function useMousePosition() {
  const [position, setPosition] = useState({
    x: 0,
    y: 0,
  });

  function onMouseMove(
    event: React.MouseEvent<HTMLDivElement>
  ) {
    setPosition({
      x: event.clientX,
      y: event.clientY,
    });
  }

  return {
    ...position,
    onMouseMove,
  };
}
```

Again, this illustrates the pattern; your actual hook implementation may differ.

The hook returns a JavaScript object:

```
{
  x: position.x,
  y: position.y,
  onMouseMove: onMouseMove
}
```

Your component destructures that object:

```
const { x, y, onMouseMove } = useMousePosition();
```

This is ordinary JavaScript object destructuring. The hook provides values and a function, and the component decides how to use them.

## 2.2 How does the data flow?

`useMousePosition()`

Provides x, y and an event handler

`App`

Destructures the returned values

`onMouseMove={onMouseMove}`

Attaches the handler to the chosen element

Mouse event → state update → re-render

App displays the latest coordinates

There is an important design difference here: the hook returns the event handler, but it does not decide which element receives it.

The component decides:

```
<div
  className="relative-container"
  onMouseMove={onMouseMove}
>
```

You could attach the same handler to a different element without changing the hook itself.

The hook shares the logic. The component controls the UI and event wiring.

# 3. The fundamental difference: what does each pattern abstract?

This is the most important part to understand.

Both patterns can reuse the same underlying state and event-handling logic. They differ in how that logic is exposed to the component using it.

## Render Props: share behavior through a rendering contract

The render-props component effectively says:

> "I can track the mouse. Give me a function that tells me what you want to render using the position I provide."

The consumer passes a function:

```
<RenderMousePosition>
  {position => /* return some UI */}
</RenderMousePosition>
```

The wrapper invokes that function and renders its result.

The consumer's rendering logic is passed into the component.

## Custom Hook: share behavior through a JavaScript interface

The custom hook effectively says:

> "I can provide mouse-tracking state and an event handler. Use them however you want in your component."

The consumer calls a function:

```
const { x, y, onMouseMove } = useMousePosition();
```

The component then uses those values in its own JSX.

The reusable logic is called by the consumer, rather than being exposed through a wrapper component.

| Question                                      | Render Props                         | Custom Hook                               |
| --------------------------------------------- | ------------------------------------ | ----------------------------------------- |
| What is passed into the abstraction?          | A rendering function                 | Usually nothing beyond optional arguments |
| What does the abstraction expose?             | Data supplied to the render function | Values and functions returned by the hook |
| Who writes the rendered JSX?                  | The consumer's callback              | The component calling the hook            |
| Does the pattern require a wrapper component? | Yes, by design                       | No                                        |
| Where is reusable logic used?                 | Inside the wrapper component         | Inside the component calling the hook     |

The deeper distinction is that a render prop is a component composition pattern, whereas a custom hook is a logic-reuse pattern built on JavaScript functions and React's Hook mechanism.

They overlap in what they can accomplish, but their interfaces are different.

# 4. Why does a custom hook not need to return JSX?

Because a custom hook is not responsible for rendering a component.

Consider:

```
function useCounter() {
  const [count, setCount] = useState(0);

  return { count, setCount };
}
```

The hook returns data and behavior. The component determines how that data becomes UI:

```
function Counter() {
  const { count, setCount } = useCounter();

  return (
    <button onClick={() => setCount(count + 1)}>
      Count: {count}
    </button>
  );
}
```

The hook doesn't have to know whether the counter will be displayed in a button, a heading, a chart, or a custom control.

This separation is one of the main benefits of custom hooks.

A render-props implementation instead allows a component to receive the rendering function:

```
<CounterProvider>
  {({ count, increment }) => (
    <button onClick={increment}>
      Count: {count}
    </button>
  )}
</CounterProvider>
```

Both separate behavior from presentation, but the custom hook usually does so with less component-level indirection.

# 5. Does the custom hook make the code more reusable?

Not automatically. Both approaches can be reusable.

Suppose you want mouse coordinates for:

- A coordinate display.
- A custom cursor.
- A drawing surface.
- A tooltip that follows the pointer.

With render props, each consumer supplies a different render function.

With a hook, each consumer calls `useMousePosition()` and uses the returned state and handler in its own JSX.

The hook is often more flexible when the consumer needs to combine mouse tracking with other local state, event handlers, or layout logic. But a render-props component can still be useful when the abstraction intentionally owns a wrapper or needs to control how its child is rendered.

One caveat: if the hook attaches its event listener internally to a fixed global target, its interface may be less flexible than one that returns a handler. The exact behavior depends on the hook's implementation, not merely on the fact that it is a custom hook.

# 6. How TypeScript models the two patterns

TypeScript makes the contracts explicit.

## Render Props

```
type Position = {
  x: number;
  y: number;
};

type RenderMousePositionProps = {
  children: (position: Position) => React.ReactNode;
};
```

This says that the component expects `children` to be a function that receives a `Position` and returns something React can render.

The function's parameter is typed, so TypeScript knows that the callback receives `x` and `y` as numbers.

## Custom Hook

```
type MousePositionResult = {
  x: number;
  y: number;
  onMouseMove: (
    event: React.MouseEvent<HTMLDivElement>
  ) => void;
};
```

This describes the hook's returned interface.

Conceptually, its signature is:

```
function useMousePosition(): MousePositionResult
```

The hook returns an object with two numeric coordinates and a mouse-event handler.

Notice the distinction: the render-props API specifies a callback contract; the hook API specifies a return-value contract.

# 7. Common mistakes and important details

### Mistake 1: assuming `children` must be JSX

In ordinary JSX, `children` is often an element or text. But a component can explicitly accept and invoke a function as its `children` prop.

```
{children(position)}
```

That invocation is what makes this a render-props pattern.

### Mistake 2: thinking a custom hook shares state between components

If two components independently call a hook containing `useState`, each call generally creates its own state instance.

```
function A() {
  const position = useMousePosition();
}

function B() {
  const position = useMousePosition();
}
```

These two calls do not automatically share one mouse-position state. They share the hook's logic, not a singleton state store.

To share one source of state, you need a shared owner or another shared-state mechanism.

### Mistake 3: assuming both examples calculate the same coordinates

The code shown doesn't include the actual implementations of `RenderMousePosition` or `useMousePosition`. We therefore cannot conclude that their coordinate systems are identical.

For example:

- `event.clientX` and `event.clientY` are viewport-relative.
- `event.pageX` and `event.pageY` are document-relative.
- `event.currentTarget.getBoundingClientRect()` can be used to calculate coordinates relative to an element.

The chosen calculation determines the meaning of the coordinates.

### Mistake 4: thinking hooks replace every render prop

Hooks are often preferable for sharing stateful logic in function components, but render props remain a valid composition pattern. Choose based on the abstraction's needs rather than treating one as universally wrong.

# 8. Interview-ready summary

| Topic                                                     | Answer                                                                           |
| --------------------------------------------------------- | -------------------------------------------------------------------------------- |
| What is a render prop?                                    | A function prop that a component invokes to determine what to render.            |
| What is a custom hook?                                    | A function that uses React Hooks to reuse stateful or other React-related logic. |
| Why use render props?                                     | To share behavior while allowing consumers to customize the rendered UI.         |
| Why use custom hooks?                                     | To share logic without requiring a wrapper component.                            |
| Which is generally preferred for new function components? | Custom hooks for reusable logic, when they fit the requirement.                  |
| Do separate hook calls share state?                       | No, not automatically.                                                           |
| Does a custom hook control rendering?                     | Not inherently; its caller normally owns the JSX.                                |
