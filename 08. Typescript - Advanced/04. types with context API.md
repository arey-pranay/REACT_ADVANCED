# TypeScript + React: Typing the Context API

The most important thing to understand is that Context shares a value; TypeScript defines the shape of that value.

Context itself does not manage state. You can use it to share a simple value, a state setter, a reducer's `dispatch`, or a custom object containing several values and functions.

We'll build this from simple examples to a typed Context + `useReducer` setup.

## 1. Why do we need Context API?

Imagine a component tree:

```
App
 └── Dashboard
      └── UserProfile
           └── Avatar
```

Suppose `App` has the logged-in user's information, and `Avatar` needs the user's name.

Without Context, you might pass the value through every intermediate component:

```
<App user={user} />
<Dashboard user={user} />
<UserProfile user={user} />
<Avatar user={user} />
```

This is called prop drilling.

Context lets a component provide a value to descendants without manually passing it through every level.

```
UserContext.Provider
        |
        v
     Dashboard
        |
        v
    UserProfile
        |
        v
      Avatar
        |
        v
   useContext(UserContext)
```

Context is useful for shared values such as themes, authenticated-user data, locale, and application state.

It does not automatically replace every state-management library. For complex server-state caching, for example, a dedicated data-fetching library may be more appropriate.

## 2. Create a typed Context

Suppose we want to share a user's name.

First, define the data type:

```
type User = {
  id: number;
  name: string;
  email: string;
};
```

Next, create the Context:

```
import { createContext } from "react";

const UserContext = createContext<User | null>(null);
```

Let's understand the generic:

```
createContext<User | null>(null);
```

- `User` describes the value when a user exists.
- `null` represents the absence of a user.
- `createContext<T>()` tells TypeScript what values the Context can hold.
- The argument `null` is the default value used when there is no matching Provider above the consumer.

The resulting Context value has the type:

```
User | null
```

This is better than using `any`, because TypeScript can check how consumers use the value.

## 3. Create the Provider component

Creating a Context doesn't make the value available by itself. A component must provide the value.

```
import { createContext } from "react";

type User = {
  id: number;
  name: string;
  email: string;
};

const UserContext = createContext<User | null>(null);

function App() {
  const user: User = {
    id: 1,
    name: "Pranay",
    email: "pranay@example.com",
  };

  return (
    <UserContext.Provider value={user}>
      <Dashboard />
    </UserContext.Provider>
  );
}
```

The key is:

```
<UserContext.Provider value={user}>
  <Dashboard />
</UserContext.Provider>
```

TypeScript checks that `user` matches `User | null`.

For example, this is invalid:

```
<UserContext.Provider value={{ name: "Pranay" }}>
  <Dashboard />
</UserContext.Provider>
```

The object is missing `id` and `email`.

### How does a consumer access the value?

Use `useContext`:

```
import { useContext } from "react";

function Avatar() {
  const user = useContext(UserContext);

  if (user === null) {
    return <p>No user logged in</p>;
  }

  return <p>Hello, {user.name}</p>;
}
```

Before the null check, `user` is `User | null`. After the check, TypeScript knows that `user` is a `User`.

This is called type narrowing.

## 4. Why use `null` as the default Context value?

A common question is why we don't simply write:

```
const UserContext = createContext<User>({} as User);
```

This uses a type assertion to tell TypeScript to trust us, even though `{}` doesn't actually satisfy the `User` type.

That can hide errors. A component might try to access `user.name` when no user was provided, and the missing value could cause a runtime problem.

A safer pattern is:

```
const UserContext = createContext<User | null>(null);
```

This forces consumers to account for the possibility that the user is absent.

For required application Contexts, we can go one step further and create a custom hook that throws a clear error when the Provider is missing.

## 5. Create a custom hook for Context

Instead of repeating this in every component:

```
const user = useContext(UserContext);

if (user === null) {
  throw new Error("UserContext Provider is missing");
}
```

Create a reusable hook:

```
import { createContext, useContext } from "react";

type User = {
  id: number;
  name: string;
  email: string;
};

const UserContext = createContext<User | null>(null);

export function useUser(): User {
  const user = useContext(UserContext);

  if (user === null) {
    throw new Error("useUser must be used within UserProvider");
  }

  return user;
}
```

Now any consumer can write:

```
function Avatar() {
  const user = useUser();

  return <p>Hello, {user.name}</p>;
}
```

The return type of `useUser()` is simply `User`, not `User | null`, because the hook checks the value before returning it.

This gives us two benefits:

1. Consumers don't have to repeat the null check.
2. A missing Provider produces a clear error instead of allowing an invalid value to flow through the component.

In a real application, you would usually export `UserProvider` and `useUser` from a dedicated Context file.

## 6. Type `PropsWithChildren`

A Provider component typically wraps other components:

```
<UserProvider>
  <Dashboard />
</UserProvider>
```

The Provider therefore needs a `children` prop.

React provides the `PropsWithChildren` utility type for this.

```
import type { PropsWithChildren } from "react";

type UserProviderProps = PropsWithChildren;
```

Conceptually, `PropsWithChildren` adds an optional `children` property to a props type.

When your component also has its own props, pass them as a generic:

```
type CardProps = {
  title: string;
};

type CardWithChildrenProps = PropsWithChildren<CardProps>;
```

This is approximately equivalent to:

```
type CardWithChildrenProps = {
  title: string;
  children?: React.ReactNode;
};
```

You can then write:

```
function Card({ title, children }: CardWithChildrenProps) {
  return (
    <section>
      <h2>{title}</h2>
      {children}
    </section>
  );
}
```

Usage:

```
<Card title="Profile">
  <p>User details go here.</p>
</Card>
```

### `PropsWithChildren<T>` vs `ReactNode`

These are not interchangeable:

- `PropsWithChildren<T>` describes a props object that includes optional `children`.
- `React.ReactNode` describes the kinds of values React can render as children, such as elements, strings, numbers, arrays of nodes, and `null`.

For example:

```
type ProviderProps = React.PropsWithChildren<{
  initialName: string;
}>;
```

Here, `initialName` is your own prop, and `children` is added by the utility type.

You can also type `children` explicitly:

```
type ProviderProps = {
  initialName: string;
  children: React.ReactNode;
};
```

Use the explicit form when children are required. `PropsWithChildren<T>` makes `children` optional, which is often appropriate for providers but isn't always what you want.

## 7. Context with `useState`

Now let's create a Provider that owns state rather than providing a fixed object.

We want to share a counter and its setter.

```
import {
  createContext,
  useContext,
  useState,
} from "react";
import type {
  Dispatch,
  SetStateAction,
  PropsWithChildren,
} from "react";

type CounterContextType = {
  count: number;
  setCount: Dispatch<SetStateAction<number>>;
};

const CounterContext = createContext<CounterContextType | null>(null);

export function CounterProvider({
  children,
}: PropsWithChildren) {
  const [count, setCount] = useState<number>(0);

  return (
    <CounterContext.Provider value={{ count, setCount }}>
      {children}
    </CounterContext.Provider>
  );
}

export function useCounter(): CounterContextType {
  const context = useContext(CounterContext);

  if (context === null) {
    throw new Error("useCounter must be used within CounterProvider");
  }

  return context;
}
```

A consumer can now read and update the same counter:

```
function CounterDisplay() {
  const { count } = useCounter();

  return <p>Count: {count}</p>;
}

function CounterButtons() {
  const { setCount } = useCounter();

  return (
    <button onClick={() => setCount((prev) => prev + 1)}>
      Increment
    </button>
  );
}
```

### Understand the setter type

```
Dispatch<SetStateAction<number>>
```

This is the same setter type returned by `useState<number>()`.

It accepts either a number:

```
setCount(10);
```

or an updater function:

```
setCount((prev) => prev + 1);
```

If you typed it as just `(count: number) => void`, the updater-function form would no longer be accepted.

### Why define `CounterContextType`?

Without a named type, the Context's value shape can be harder to reuse or understand.

```
type CounterContextType = {
  count: number;
  setCount: Dispatch<SetStateAction<number>>;
};
```

This clearly documents the contract between the Provider and all consumers.

## 8. Context with `useReducer`

This is where the previous topics — `State`, `Action`, `Reducer`, and `Dispatch` — come together.

Imagine a shared counter used by several components. Instead of passing a state setter, we expose a `dispatch` function that accepts predefined actions.

### Step 1: Define the state and actions

```
type State = {
  count: number;
};

type Action =
  | { type: "increment" }
  | { type: "decrement" }
  | { type: "reset" }
  | { type: "add"; payload: number };

const initialState: State = {
  count: 0,
};
```

### Step 2: Create the reducer

```
import type { Reducer } from "react";

const reducer: Reducer<State, Action> = (state, action) => {
  switch (action.type) {
    case "increment":
      return { count: state.count + 1 };

    case "decrement":
      return { count: state.count - 1 };

    case "reset":
      return initialState;

    case "add":
      return { count: state.count + action.payload };
  }
};
```

The reducer determines the next state based on the current state and the action.

### Step 3: Create two Contexts

```
import { createContext } from "react";
import type { Dispatch } from "react";

const CounterStateContext = createContext<State | null>(null);

const CounterDispatchContext =
  createContext<Dispatch<Action> | null>(null);
```

Why two Contexts?

- `CounterStateContext` provides the current state.
- `CounterDispatchContext` provides the function for requesting state changes.

The dispatch function has this type:

```
Dispatch<Action>
```

It accepts only valid `Action` objects.

### Step 4: Create the Provider

```
import { useReducer } from "react";
import type { PropsWithChildren } from "react";

export function CounterProvider({
  children,
}: PropsWithChildren) {
  const [state, dispatch] = useReducer(reducer, initialState);

  return (
    <CounterStateContext.Provider value={state}>
      <CounterDispatchContext.Provider value={dispatch}>
        {children}
      </CounterDispatchContext.Provider>
    </CounterStateContext.Provider>
  );
}
```

The Provider owns the reducer. Its descendants receive access to the state, dispatch, or both.

### Step 5: Create custom hooks

```
import { useContext } from "react";

export function useCounterState(): State {
  const state = useContext(CounterStateContext);

  if (state === null) {
    throw new Error(
      "useCounterState must be used within CounterProvider"
    );
  }

  return state;
}

export function useCounterDispatch(): Dispatch<Action> {
  const dispatch = useContext(CounterDispatchContext);

  if (dispatch === null) {
    throw new Error(
      "useCounterDispatch must be used within CounterProvider"
    );
  }

  return dispatch;
}
```

Now consumers have a clean API.

A component that only reads the count:

```
function CounterDisplay() {
  const { count } = useCounterState();

  return <p>Count: {count}</p>;
}
```

A component that only dispatches actions:

```
function CounterControls() {
  const dispatch = useCounterDispatch();

  return (
    <>
      <button onClick={() => dispatch({ type: "increment" })}>
        Increment
      </button>

      <button onClick={() => dispatch({ type: "decrement" })}>
        Decrement
      </button>

      <button onClick={() => dispatch({ type: "add", payload: 5 })}>
        Add 5
      </button>

      <button onClick={() => dispatch({ type: "reset" })}>
        Reset
      </button>
    </>
  );
}
```

Finally, wrap the relevant part of the component tree:

```
function App() {
  return (
    <CounterProvider>
      <CounterDisplay />
      <CounterControls />
    </CounterProvider>
  );
}
```

### Understand the architecture

CounterProvider

Owns useReducer(reducer, initialState)

State Context

Current state

For readers

Dispatch Context

Dispatch function

For action senders

Both are available to descendants within the Provider.

This pattern is particularly useful when many components share the same state and the state transitions are more complex than a few simple setters.

## 9. Why separate State and Dispatch Contexts?

React's `useReducer` dispatch function has a stable identity for a mounted component. Separating the Contexts can help avoid unnecessary Context-driven renders.

Suppose a component only needs to dispatch actions:

```
function IncrementButton() {
  const dispatch = useCounterDispatch();

  return (
    <button onClick={() => dispatch({ type: "increment" })}>
      Increment
    </button>
  );
}
```

When the reducer state changes:

- The State Context value changes.
- The Dispatch Context value stays the same.
- `IncrementButton` does not need to re-render due to a change in the Dispatch Context value alone.

However, separating Contexts does not prevent every re-render. A component can still re-render because its parent renders, its own state changes, or another Context it consumes changes.

For small applications, a single Context containing `{ state, dispatch }` is often simpler. Separate them when it meaningfully improves the subscription structure.

## 10. Alternative: one Context for both state and dispatch

You can also combine both into a single Context.

```
type CounterContextType = {
  state: State;
  dispatch: Dispatch<Action>;
};

const CounterContext =
  createContext<CounterContextType | null>(null);
```

Provider:

```
function CounterProvider({ children }: PropsWithChildren) {
  const [state, dispatch] = useReducer(reducer, initialState);

  return (
    <CounterContext.Provider value={{ state, dispatch }}>
      {children}
    </CounterContext.Provider>
  );
}
```

Consumer:

```
function CounterDisplay() {
  const context = useContext(CounterContext);

  if (context === null) {
    throw new Error("CounterProvider is missing");
  }

  return <p>{context.state.count}</p>;
}
```

This is straightforward, but there's a detail worth knowing: `{ state, dispatch }` creates a new object when the Provider renders. Context consumers can re-render when that object changes by identity.

For larger applications, consider separate Contexts, carefully designed state boundaries, or a state-management library if profiling shows a problem.

## 11. Typing Context with custom data and functions

Context doesn't have to expose a reducer. It can provide a service-like object with data and functions.

For example, an authentication Context:

```
type User = {
  id: string;
  name: string;
};

type AuthContextType = {
  user: User | null;
  isAuthenticated: boolean;
  login: (user: User) => void;
  logout: () => void;
};
```

Each field has a distinct meaning:

| Field             | Type                   | Purpose                                            |
| ----------------- | ---------------------- | -------------------------------------------------- |
| `user`            | `User \\| null`        | The current user, if logged in                     |
| `isAuthenticated` | `boolean`              | Whether the user is authenticated                  |
| `login`           | `(user: User) => void` | Accepts a user and returns no meaningful value     |
| `logout`          | `() => void`           | Takes no arguments and returns no meaningful value |

Create the Context:

```
const AuthContext = createContext<AuthContextType | null>(null);
```

This declaration tells TypeScript the exact shape the Provider must supply.

For example, a `login` function that expects a string instead of a `User` would not satisfy the declared type.

The general pattern is:

```
type SomeContextType = {
  // Shared data
  value: string;

  // Shared functions
  updateValue: (nextValue: string) => void;
};

const SomeContext =
  createContext<SomeContextType | null>(null);
```

## 12. Typing Context in Next.js

The Context API works in Next.js, but the App Router has an important distinction: Context Providers and components that use state or Context must be Client Components.

A common setup looks like this:

```
// app/providers.tsx
"use client";

import { createContext, useContext, useState } from "react";
import type { PropsWithChildren } from "react";

type Theme = "light" | "dark";

type ThemeContextType = {
  theme: Theme;
  toggleTheme: () => void;
};

const ThemeContext = createContext<ThemeContextType | null>(null);

export function ThemeProvider({ children }: PropsWithChildren) {
  const [theme, setTheme] = useState<Theme>("light");

  function toggleTheme() {
    setTheme((current) =>
      current === "light" ? "dark" : "light"
    );
  }

  return (
    <ThemeContext.Provider value={{ theme, toggleTheme }}>
      {children}
    </ThemeContext.Provider>
  );
}

export function useTheme() {
  const context = useContext(ThemeContext);

  if (context === null) {
    throw new Error("useTheme must be used within ThemeProvider");
  }

  return context;
}
```

Use the Provider from a layout:

```
// app/layout.tsx
import { ThemeProvider } from "./providers";
import type { PropsWithChildren } from "react";

export default function RootLayout({
  children,
}: PropsWithChildren) {
  return (
    <html lang="en">
      <body>
        <ThemeProvider>{children}</ThemeProvider>
      </body>
    </html>
  );
}
```

The layout can remain a Server Component. Importing a Client Component Provider does not force the entire layout file to become a Client Component.

The Provider creates the client-side state boundary, while the layout can continue to render server-side content.

## 13. Common TypeScript mistakes with Context

### Mistake A: Using `any`

```
const Context = createContext<any>(null);
```

This removes most of the type safety that Context could provide.

Prefer:

```
type ContextValue = {
  name: string;
};

const Context = createContext<ContextValue | null>(null);
```

### Mistake B: Forgetting that the default value can be `null`

```
const value = useContext(Context);
console.log(value.name);
```

If the Context type includes `null`, you must narrow it first or use a custom hook that performs the check.

### Mistake C: Confusing the state type with the Context value type

For example:

```
type State = {
  count: number;
};

type CounterContextType = {
  state: State;
  dispatch: Dispatch<Action>;
};
```

These are different types:

- `State` describes the reducer's state.
- `CounterContextType` describes everything exposed by the Context.

### Mistake D: Using the wrong setter type

For `useState`:

```
Dispatch<SetStateAction<number>>
```

For `useReducer`:

```
Dispatch<Action>
```

Choose based on the function you're exposing.

### Mistake E: Forgetting the Provider

A custom hook that throws when the Provider is missing helps catch this immediately. Without that guard, consumers may accidentally work with the default value instead of the intended application state.

## 14. Revision cheatsheet

| Concept                                               | Pattern                                                   |
| ----------------------------------------------------- | --------------------------------------------------------- |
| Create typed Context                                  | `createContext<Value \\| null>(null)`                     |
| Read Context                                          | `useContext(MyContext)`                                   |
| Provide a value                                       | `<MyContext.Provider value={value}>`                      |
| Type Provider children                                | `PropsWithChildren`                                       |
| Type a `useState` setter                              | `Dispatch<SetStateAction<T>>`                             |
| Type a reducer dispatch                               | `Dispatch<Action>`                                        |
| Type a reducer                                        | `Reducer<State, Action>`                                  |
| Protect consumers                                     | Custom hook with a null check                             |
| Avoid state subscriptions in dispatch-only components | Separate State and Dispatch Contexts                      |
| Next.js App Router                                    | Put stateful Context logic in a Client Component Provider |

One-line mental model: `createContext<T>` defines the shared value's contract, the Provider supplies a value matching that contract, and `useContext` reads it; TypeScript keeps the Provider and consumers consistent.
