# TypeScript Advanced Types — Generics, Type Helpers, Interfaces, Hooks & Function Overloads

These topics build on `keyof`, `typeof`, indexed access (`T[K]`), unions, intersections, and utility types.

The central idea is that TypeScript lets us describe relationships between values and types, not just assign types to individual variables.

We'll use practical examples from regular TypeScript and React.

## 1. Type helpers (type aliases and reusable types)

A type helper is a reusable type definition that simplifies a more complex type or avoids repeating the same structure.

TypeScript doesn't have a special `type helper` keyword. It's a general term for reusable type definitions.

### A. Extract a reusable object shape

Instead of repeating this:

```
function createBook(title: string, price: number) {
  return { title, price };
}

function updateBook(title: string, price: number) {
  return { title, price };
}
```

Define the shape once:

```
type Book = {
  title: string;
  price: number;
};

function createBook(title: string, price: number): Book {
  return { title, price };
}

function updateBook(title: string, price: number): Book {
  return { title, price };
}
```

Now both functions share the same contract.

### B. Derive types instead of duplicating them

```
type Book = {
  title: string;
  price: number;
  author: string;
};

type BookPreview = Pick<Book, "title" | "price">;
type BookUpdate = Partial<Book>;
type BookWithoutAuthor = Omit<Book, "author">;
```

These helpers stay connected to `Book`. If `Book` changes, the derived types update automatically where appropriate.

### C. Build your own helper

```
type Nullable<T> = T | null;

type MaybeBook = Nullable<Book>;
// Book | null
```

Another example:

```
type ApiResponse<T> = {
  data: T;
  success: boolean;
  error?: string;
};

type BookResponse = ApiResponse<Book>;
type BooksResponse = ApiResponse<Book[]>;
```

The same response structure works for a single book, a list of books, or another data type.

When to use type helpers: when the same type structure appears in several places, or when a complex type becomes difficult to read inline.

## 2. Generic constraints

A generic parameter allows a function or type to work with different types. A constraint restricts which types are allowed.

### A. Unconstrained generic

```
function identity<T>(value: T): T {
  return value;
}
```

`T` can be a string, number, object, array, or another type.

But TypeScript won't let you access arbitrary properties on `T`:

```
function getLength<T>(value: T) {
  return value.length; // Error
}
```

Why? `T` could be a number, which doesn't have a `length` property.

### B. Add a constraint using `extends`

```
function getLength<T extends { length: number }>(
  value: T
): number {
  return value.length;
}
```

Now `T` must have a numeric `length`.

```
getLength("hello");       // 5
getLength([10, 20, 30]);  // 3

getLength(123);           // Type error
```

The generic still preserves the specific input type. The constraint simply guarantees that `length` exists.

### C. Constrain a generic to an object's keys

```
function getProperty<T, K extends keyof T>(
  obj: T,
  key: K
): T[K] {
  return obj[key];
}
```

Usage:

```
const book = {
  title: "Clean Code",
  price: 500,
};

const title = getProperty(book, "title"); // string
const price = getProperty(book, "price"); // number
```

This line is the key:

```
K extends keyof T
```

It means `K` must be a valid key of `T`.

And:

```
T[K]
```

means the value type associated with that particular key.

### D. Constrain an object to have an ID

```
type HasId = {
  id: string | number;
};

function getId<T extends HasId>(item: T) {
  return item.id;
}
```

This can work with users, products, books, or other objects that have a compatible `id` property.

```
getId({ id: 10, name: "Sam" });       // Valid
getId({ id: "book-1", title: "TS" });  // Valid
getId({ name: "Sam" });               // Type error
```

Mental model: a generic gives flexibility; `extends` sets the minimum requirements for that flexibility.

## 3. Generic interfaces

An interface can itself have a generic parameter.

### A. Generic interface for API responses

```
interface ApiResponse<T> {
  data: T;
  success: boolean;
}
```

Use the same interface for different data types:

```
type Book = {
  title: string;
  price: number;
};

const bookResponse: ApiResponse<Book> = {
  data: { title: "Clean Code", price: 500 },
  success: true,
};

const booksResponse: ApiResponse<Book[]> = {
  data: [
    { title: "Clean Code", price: 500 },
    { title: "The Pragmatic Programmer", price: 700 },
  ],
  success: true,
};
```

`T` is a placeholder that gets replaced with the chosen type.

```
ApiResponse<Book>     → data: Book
ApiResponse<Book[]>   → data: Book[]
ApiResponse<string>   → data: string
```

Without generics, you might create separate interfaces for every kind of response. A generic interface lets you reuse the structure.

### B. Generic interface for a function

```
interface Transformer<T, U> {
  (value: T): U;
}
```

This describes a function that accepts `T` and returns `U`.

```
const toLength: Transformer<string, number> = (value) => {
  return value.length;
};

const toUpperCase: Transformer<string, string> = (value) => {
  return value.toUpperCase();
};
```

The interface describes the function's contract. The implementation provides its behavior.

### C. Generic interface for a data structure

```
interface Repository<T> {
  getAll(): T[];
  getById(id: string): T | undefined;
  save(item: T): void;
}
```

A repository for books and a repository for users can implement the same contract while retaining different data types.

```
type Book = {
  id: string;
  title: string;
};

const bookRepository: Repository<Book> = {
  getAll: () => [],
  getById: (id) => undefined,
  save: (book) => {
    console.log(book.title);
  },
};
```

A generic interface is especially useful when multiple implementations should follow the same structure but work with different types.

## 4. Generic functions vs generic interfaces vs generic types

These concepts look similar because all of them use type parameters, but they serve different purposes.

| Feature                 | Example                                 | What it describes                             |
| ----------------------- | --------------------------------------- | --------------------------------------------- |
| Generic function        | `function identity<T>(x: T): T`         | A reusable operation                          |
| Generic interface       | `interface Box<T> { value: T }`         | A reusable contract                           |
| Generic type alias      | `type Box<T> = { value: T }`            | A reusable type definition                    |
| Generic class           | `class Box<T> { value: T }`             | A reusable class and its instances            |
| Generic React component | `function List<T>(props: ListProps<T>)` | A component that renders different data types |
| Generic hook            | `function useItem<T>(initial: T)`       | A hook that preserves the data type           |

All use the same underlying principle: a type parameter represents a type supplied or inferred at the point of use.

## 5. Generic React components

Suppose we want a component that displays a list of items.

A basic implementation might work only for strings:

```
type StringListProps = {
  items: string[];
};

function StringList({ items }: StringListProps) {
  return (
    <ul>
      {items.map((item) => (
        <li key={item}>{item}</li>
      ))}
    </ul>
  );
}
```

But what if we want to display users, books, or products too?

We could write separate components for each type. A generic component avoids that duplication.

### A. Define generic props

```
type ListProps<T> = {
  items: T[];
  renderItem: (item: T) => React.ReactNode;
};
```

Here:

- `T[]` means an array of items of type `T`.
- `renderItem` receives one item of that same type.
- `React.ReactNode` is the range of renderable React content returned by the callback.

### B. Create the generic component

```
function List<T>({ items, renderItem }: ListProps<T>) {
  return (
    <ul>
      {items.map((item, index) => (
        <li key={index}>{renderItem(item)}</li>
      ))}
    </ul>
  );
}
```

The component can render any item type, as long as the supplied callback knows how to render it.

### C. Use it with strings

```
<List
  items={["React", "TypeScript", "Next.js"]}
  renderItem={(item) => <span>{item.toUpperCase()}</span>}
/>
```

TypeScript infers `T` as `string`. Therefore, `item.toUpperCase()` is valid.

### D. Use it with objects

```
type User = {
  id: number;
  name: string;
  email: string;
};

const users: User[] = [
  { id: 1, name: "Alice", email: "alice@example.com" },
  { id: 2, name: "Bob", email: "bob@example.com" },
];

<List
  items={users}
  renderItem={(user) => (
    <span>
      {user.name} — {user.email}
    </span>
  )}
/>
```

Now `T` is inferred as `User`, so TypeScript knows that `user.name` and `user.email` exist.

### E. Explicitly provide the generic type

Usually, inference is enough. But you can specify the type yourself:

```
<List<User>
  items={users}
  renderItem={(user) => <span>{user.name}</span>}
/>
```

This is helpful when TypeScript cannot infer the intended type or when you want to make the component's expected data type explicit.

### When to use generic components

Use them when the component's structure stays the same but the data type varies.

Examples:

- Lists and tables.
- Select or dropdown components.
- Reusable data grids.
- Generic form fields.
- Components that accept a render callback.

Don't make a component generic just because you can. If it always displays a particular `User` shape, a simple `User` prop type may be clearer.

## 6. Generic hooks

A custom hook can also be generic. This is useful when the hook manages or returns values whose types vary between usages.

### A. Simple generic hook

```
import { useState } from "react";

function useValue<T>(initialValue: T) {
  const [value, setValue] = useState<T>(initialValue);

  return { value, setValue };
}
```

Usage:

```
const name = useValue("Pranay");
// value: string

const count = useValue(0);
// value: number

const selectedUser = useValue<User | null>(null);
// value: User | null
```

The generic parameter preserves the type throughout the hook.

### B. Generic hook with a constraint

Imagine a hook that stores a selected item by its ID.

```
type HasId = {
  id: string | number;
};

function useSelection<T extends HasId>() {
  const [selected, setSelected] = useState<T | null>(null);

  return { selected, setSelected };
}
```

Usage:

```
type Product = {
  id: number;
  name: string;
  price: number;
};

const { selected, setSelected } = useSelection<Product>();
```

`Product` satisfies the constraint because it has a compatible `id`.

The hook can work with different entity types, but it guarantees that every selected item has an ID.

### C. A generic hook for fetching data

```
import { useEffect, useState } from "react";

function useFetch<T>(url: string) {
  const [data, setData] = useState<T | null>(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const controller = new AbortController();

    async function load() {
      try {
        setLoading(true);
        setError(null);

        const response = await fetch(url, {
          signal: controller.signal,
        });

        if (!response.ok) {
          throw new Error(`Request failed: ${response.status}`);
        }

        const result = (await response.json()) as T;
        setData(result);
      } catch (err) {
        if (err instanceof Error && err.name !== "AbortError") {
          setError(err.message);
        }
      } finally {
        if (!controller.signal.aborted) {
          setLoading(false);
        }
      }
    }

    void load();

    return () => controller.abort();
  }, [url]);

  return { data, loading, error };
}
```

Usage:

```
type User = {
  id: number;
  name: string;
};

const { data, loading, error } = useFetch<User>("/api/user");
```

Important limitation: `as T` is a type assertion, not runtime validation. It tells TypeScript to treat the parsed JSON as `T`; it does not prove that the server actually returned a valid `User`. For untrusted API responses, validate the data at runtime with a schema or explicit checks.

For production applications with caching, request deduplication, retries, and background revalidation, a data-fetching library is often preferable to building all that behavior into a custom hook.

## 7. `interface` vs `type`

Both can describe object shapes, and many React props can be written using either. The important differences are what they can represent and how they behave when declarations are repeated.

### A. `interface` for object contracts

```
interface User {
  id: number;
  name: string;
}

interface Admin extends User {
  permissions: string[];
}
```

An interface can extend another interface, adding more requirements.

### B. `type` for aliases and type expressions

```
type User = {
  id: number;
  name: string;
};

type Admin = User & {
  permissions: string[];
};
```

Type aliases can represent object shapes too, but also unions, primitives, tuples, conditional types, and more.

```
type ID = string | number;

type Status = "loading" | "success" | "error";

type Coordinates = [number, number];
```

An interface cannot directly represent a union such as `string | number`.

### C. Declaration merging

Interfaces with the same name can be merged:

```
interface User {
  id: number;
}

interface User {
  name: string;
}
```

The resulting `User` interface has both `id` and `name`.

Regular type aliases cannot be redeclared with the same name in the same scope:

```
type User = { id: number };
type User = { name: string }; // Error
```

### D. Quick comparison

| Feature                         | `interface`      | `type` |
| ------------------------------- | ---------------- | ------ |
| Describe object shapes          | Yes              | Yes    |
| Extend/combine object shapes    | `extends`        | `&`    |
| Represent unions                | No, not directly | Yes    |
| Represent primitives and tuples | No, not directly | Yes    |
| Conditional and mapped types    | No, not directly | Yes    |
| Declaration merging             | Yes              | No     |
| Generic definitions             | Yes              | Yes    |

### Which should you use in React?

Both are valid:

```
interface ButtonProps {
  label: string;
  disabled?: boolean;
}
```

```
type ButtonProps = {
  label: string;
  disabled?: boolean;
};
```

A practical convention is:

- Use `interface` for extensible object contracts, especially when declaration merging or `extends` is useful.
- Use `type` for unions, intersections, utility-type transformations, conditional types, and other type expressions.
- Be consistent within a codebase.

Neither is inherently more type-safe for ordinary props.

## 8. Function overloads

Function overloads let you describe several valid ways to call one function, with different input and output types.

Suppose a function returns either a user or a list of users, depending on the input.

A single signature might look like this:

```
type User = {
  id: number;
  name: string;
};

function getUser(id: number): User;
function getUser(ids: number[]): User[];
function getUser(input: number | number[]): User | User[] {
  if (typeof input === "number") {
    return { id: input, name: "Alice" };
  }

  return input.map((id) => ({
    id,
    name: "Alice",
  }));
}
```

The first two declarations are overload signatures. The last declaration contains the actual implementation.

Usage:

```
const one = getUser(1);
// User

const many = getUser([1, 2, 3]);
// User[]
```

TypeScript gives each call a precise return type.

### Why not just use a union?

Without overloads:

```
function getUser(input: number | number[]): User | User[] {
  // ...
  throw new Error("Example");
}
```

Even when called with a single number, the declared return type is `User | User[]`. The caller may need to narrow the result before accessing `name`.

With overloads, TypeScript maps each supported input shape to its corresponding return type.

### How overloads work

```
getUser(1)
   ↓
overload: number → User

getUser([1, 2])
   ↓
overload: number[] → User[]

Both calls use one implementation.
```

### Important rule

The implementation signature is not directly exposed as a callable overload. Callers must match one of the declared overload signatures.

For example, with the overloads above:

```
getUser(1);       // Valid
getUser([1, 2]);  // Valid
getUser("Alice"); // Error
```

You must also ensure the implementation can handle every call allowed by the overloads.

## 9. Function overloads vs union parameters vs generics

These are related but solve different problems.

### A. Union parameters

Use a union when the input can take different forms and you don't need a precise input-to-output relationship.

```
function format(value: string | number): string {
  return String(value);
}
```

Both inputs produce a string.

### B. Generics

Use a generic when you want to preserve a relationship between input and output types.

```
function first<T>(items: T[]): T | undefined {
  return items[0];
}

const a = first([1, 2, 3]);      // number | undefined
const b = first(["a", "b"]);     // string | undefined
```

The return type follows the array's element type.

### C. Overloads

Use overloads when there are distinct supported call patterns and you want to specify each one clearly.

```
function parse(value: string): string[];
function parse(value: number): number;
function parse(value: string | number): string[] | number {
  if (typeof value === "string") {
    return value.split(",");
  }

  return value;
}
```

| Situation                                                    | Good starting point |
| ------------------------------------------------------------ | ------------------- |
| Multiple inputs all produce the same output type             | Union parameter     |
| Output type depends on a generic input type                  | Generic function    |
| Several distinct call signatures need different return types | Overloads           |

Don't add overloads automatically. If a generic or union signature communicates the behavior clearly, it may be simpler.

## 10. Overloads with callbacks and functions

Overloads are also useful when an API accepts different callback shapes or when the return type depends on a mode.

Consider a function that returns either a formatted string or a number.

```
function convert(value: number, mode: "text"): string;
function convert(value: string, mode: "number"): number;

function convert(
  value: number | string,
  mode: "text" | "number"
): string | number {
  if (mode === "text") {
    return String(value);
  }

  return Number(value);
}
```

Usage:

```
const a = convert(42, "text");       // string
const b = convert("42", "number");   // number
```

The overload signatures express which combinations are supported.

### A common mistake

This call is rejected:

```
declare const mode: "text" | "number";

convert(42, mode); // Error
```

Why? Neither overload accepts a union-valued `mode` with a number input. TypeScript checks whether the call matches an individual overload signature.

If union-valued arguments are part of the intended API, add a suitable overload or use a union signature that correctly describes the possible results.

### Can arrow functions have overloads?

Not directly in the same declaration style as function declarations.

You can declare an overloaded call signature through a type and assign an implementation:

```
type Convert = {
  (value: number, mode: "text"): string;
  (value: string, mode: "number"): number;
};

const convert: Convert = (value: number | string, mode: "text" | "number") => {
  if (mode === "text") {
    return String(value);
  }

  return Number(value);
};
```

However, TypeScript may reject this particular implementation because the inferred implementation return type is `string | number`, which does not satisfy each overload's return type as written. A straightforward fix is to use a function declaration with overload signatures, or use a carefully typed implementation with explicit narrowing and a compatible callable type. Function declarations are usually clearer for this pattern.

## 11. Generic components, hooks, and overloads: how to choose

Here's a practical decision guide.

### Use a generic

When the same implementation works with many types and the relationship between those types matters.

```
function identity<T>(value: T): T {
  return value;
}
```

### Use a generic constraint

When the implementation needs certain properties to exist.

```
function getId<T extends { id: string }>(value: T) {
  return value.id;
}
```

### Use a generic interface

When several implementations must satisfy a reusable contract.

```
interface Box<T> {
  value: T;
}
```

### Use a generic React component or hook

When a reusable UI component or hook needs to preserve the type of supplied data.

```
function useValue<T>(initial: T) {
  return useState<T>(initial);
}
```

### Use overloads

When different call patterns have distinct return types and you want callers to receive the correct type for each pattern.

```
function find(id: number): User;
function find(ids: number[]): User[];
```

## 12. Final revision cheatsheet

| Concept             | Core idea                                                        |
| ------------------- | ---------------------------------------------------------------- |
| Type helper         | Reusable type alias or type transformation                       |
| Generic constraint  | Restricts acceptable generic types                               |
| `K extends keyof T` | Restricts `K` to valid keys of `T`                               |
| Generic interface   | A reusable contract parameterized by types                       |
| Generic component   | Reusable UI with type-safe data                                  |
| Generic hook        | Reusable stateful logic that preserves type information          |
| `interface`         | Object contract that supports declaration merging                |
| `type`              | Flexible alias for objects, unions, tuples, and type expressions |
| Function overload   | Multiple public call signatures for one implementation           |
| Union parameter     | Accepts alternative input types                                  |
| Generic function    | Preserves relationships between input and output types           |

The most important interview distinction: generics preserve type relationships, constraints limit which types are allowed, interfaces and type aliases describe contracts, and overloads give one function multiple precise call signatures.
